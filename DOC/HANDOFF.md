## 建设顺序与依赖

1. **先做可运行的 uniGUI 骨架**：启动工程、主界面、导航、模块容器和基本异常显示。此阶段只做骨架，不提前制作大量绑定尚未确定的数据录入页面。
2. **及早取得两类事实证据**：对现有 Node-RED 做 P0 只读核对，摸清 Flow、Tag、采集/控制、缓存/转存和部署边界；以隔离 FUXA 样例验证基础 Tag 对象、稳定 ID、项目读写及人工画面引用方式。两项不依赖 uniGUI 主界面完工，可与骨架建设交错推进。FUXA 此时只验证会影响工程模型的约束，不建设完整画面和报警系统。
3. **据证据确定 SQLite 工程模型 V0.1**：定义 Node、Tag、归属/引用、协议参数、采集与存储选项、映射 ID 及数据库迁移；先用一台设备的代表性 Tag 验证模型，再建设工程配置页面。模型版本化，避免把未知 FUXA/Node-RED 字段凭猜测写死。
4. **建设统一工程配置并打通 Node-RED 主链路**：完成工程树、设备/Tag 与运行选项的配置和校验；由同一模型生成受管 Flow/参数，并按受管范围隔离部署、核对运行状态与回滚；同时生成 FUXA 稳定 Tag 目录与映射。把短期 SQLite 缓存和可选转存作为明确的部署模式验证。在隔离环境确认采集、状态、控制请求与反馈，再安排现场接入。
5. **完成 FUXA 工程同步与运行联动**：将基础设备/Tag 增量同步到 FUXA，验证再次同步差异、人工画面保护和引用检查；随后接实时显示、操作反馈、基础报警和 uniGUI 嵌入。
6. **按场景扩展**：趋势、报表、长期历史库、调度、更多设备模板、2.5D/3D 等依基础闭环和项目需求分批推进。

P0 不应独占项目起点，但必须早于 Node-RED 适配和数据库字段定版。FUXA 的关键配置约束也应早于模型定版核验；完整 FUXA 集成则排在 Node-RED 主链路之后。

- 当前计划不包含启动其他 Codex 任务；不部署、改写或重构现有正式 Node-RED/FUXA。
- 不进行生产写入、控制命令或现场 PLC 操作。

- 开发阶段可使用独立明文库加快建模与调试；不能原地解密或覆盖现有加密库，也不能把明文开发库当作生产交付。发布前须在实际加密驱动下验证同一套迁移、读写、备份与恢复。
