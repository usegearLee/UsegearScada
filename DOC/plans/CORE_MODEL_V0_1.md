# 工程对象基础模型候选

> 2026-10-01。状态：可验证的候选结构，未写入加密工程数据库；Node-RED 协议参数、缓存/转存配置和 FUXA ID 映射尚未定版。

本阶段先固定不依赖目标系统内部格式的工程关系：项目包含区域、工艺和设备节点；Tag 有一个明确的主归属节点；工艺可以引用多个 Tag，同一个 Tag 也可以被多个工艺引用。设备配套 Tag 通过 `owner_node_id` 表达 1:N，工艺复用通过 `ScadaProcessTag` 表达 N:N。节点的父子层级不自动让父工艺“拥有”所有下级设备 Tag。

候选 DDL 在 [core_model_v0_1.sql](../../DB/design/core_model_v0_1.sql)。它提供项目内唯一的节点编码与 Tag 编码、同项目外键、引用保护。项目和 Tag 使用独立稳定 ID，改显示名称不改变 ID。`node_kind`、`tag_kind`、`value_type` 暂不封闭枚举，先由配置层校验；真实协议字段不塞进这些核心表。

这份结构**没有**覆盖完整产品。接下来要核对现有 Node-RED 模板输入和 FUXA 项目对象，再设计协议地址、采集批次、缓存/转存模式、部署版本、FUXA ID 映射等扩展表。工艺节点类型、树循环、Tag 引用影响和启用控制仍需应用层验证。现有 `DB/usegear.db` 已解除文件占用，但普通 SQLite 只读连接报告“file is not a database”；现有迁移备注其为加密 SQLite。故本轮不向该库执行 DDL，也不推断其当前表结构。

另建的 `DB/dev/usegear_dev.db` 为独立明文开发库，已应用旧菜单迁移和本候选结构；完整性检查通过，工程对象表为空。它不表示应用程序已切换连接，也不构成与加密驱动兼容的验证。

验证脚本 [verify_core_model.py](../../DB/design/verify_core_model.py) 只使用内存库，验证一个设备 Tag 被两个工艺引用、跨项目所有权被拒绝、重复编码被拒绝、被引用 Tag 不能直接删除。通过这些检查只说明候选 DDL 的关系约束符合本期示例，不构成与现有加密库或 Node-RED/FUXA 接口的兼容验收。
