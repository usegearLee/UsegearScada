# 组态软件架构决策记录

> 状态：V0.1。以下是 YC 专题讨论收口的**设计决策**，不代表当前目录已有相应实现。整理日期：2026-09-29。变更决策时记录新证据、影响和替代方案，不静默覆盖。

| ID | 决策 | 理由与边界 |
|---|---|---|
| D001 | 本产品的 SQLite 是设备、Tag 等工程对象与可生成配置的唯一事实源。 | 自动同步到 FUXA 的配置在 FUXA 工程内有运行副本；工程师在 FUXA Editor 手工制作的画面布局、样式和交互由 FUXA 工程维护，不反向成为 Node/Tag 主模型，也不被自动同步覆盖。 |
| D002 | 一套工程模型经各自 Adapter 生成 Node-RED 和 FUXA 所需配置。 | 一次配置，稳定 ID，避免重复录入；生成范围须保护 FUXA 人工内容。 |
| D003 | 保留独立 Node-RED 作为唯一主工业 Runtime。 | 负责采集、计算、命令与上位调度；FUXA 内置 Node-RED 不承担第二套主运行逻辑。 |
| D004 | FUXA 承担 SCADA/HMI Editor、View、交互和基础报警。 | 不让 FUXA 对同一 PLC 再做一套采集；实际功能边界由 PoC 核验。 |
| D005 | 直接使用 FUXA Editor 做正式画面设计。 | 本阶段不自建 X6 画布；2.5D 优先，完整 3D 另作扩展评估。 |
| D006 | 设备与配套 Tag 通常 1:N；工艺与 Tag 可 N:N。 | 工艺 Tag 显式配置，通过关系表引用；下属 Tag 汇总仅是查询视图。 |
| D007 | 工程语义与 FUXA 映射分层，配置字段各有唯一维护者。 | 本产品维护 Tag、地址、周期与标准映射；FUXA 维护画面布局与特殊表现。FUXA 工程可能被人工修改，同步前必须检测差异，不能整项目覆盖。 |
| D008 | 长期 Tag 历史库不是基础系统必装项。 | 按项目、功能和 Tag 选择历史能力；PG 是长期历史及专业应用的可选扩展，不能取代 SQLite 工程配置库。 |
| D009 | 数据库访问优先原生驱动，ODBC 不作为跨平台核心依赖。 | 跨 Windows/Linux/ARM 部署时减少驱动层不确定性；具体驱动需实测。 |
| D010 | PLC 承担最终控制、联锁、安全保护和硬实时。 | FUXA 发起操作，Node-RED 路由并复核，PLC 最终判断与执行；反馈而非发命令成功决定实际状态。 |
| D011 | 调度由工程平台配置，由 Node-RED 执行。 | 统一命令入口；不依赖 uniGUI 长期运行 Timer。 |
| D012 | 界面嵌入走 URL，配置/部署走正式 API，实时值另设运行通路。 | Node-RED Admin API 与本产品 Runtime API 分离；不能用改内部数据库或频繁轮询代替正式接口。 |
| D013 | 当前不引入图数据库。 | Node/Tag、ProcessTag、依赖和拓扑先用关系模型表达，扩展以证据驱动。 |
| D014 | Node-RED 中由平台独占管理的 Flow 可重新生成并按受管范围整体替换部署。 | 受管范围不以 Editor 人工维护为常态；部署前确认目标、隔离非受管 Flow 与凭据、保留回滚版本。若受管范围出现人工修改，先报告偏离并明确维护责任。FUXA 工程仍需保护人工画面。 |

## 待验证，不作为已冻结实现

| 编号 | 问题 | 通过条件 |
|---|---|
| V001 | Node-RED ↔ FUXA 实时通道选型 | 双向值、质量、命令、PLC 反馈、断线重连与权限在隔离环境验证。 |
| V002 | FUXA 自动配置和人工编辑的同步边界 | 验证字段归属、稳定 ID、人工改动检测、冲突报告、引用检查、增量更新、备份与回滚；核实 API 是否支持安全合并。 |
| V003 | FUXA 报警历史、趋势、报表的数据依赖 | 无长期库和 PG 扩展两档分别验证；PG 只读历史适配是否需要修改 FUXA。 |
| V004 | uniGUI 嵌入 FUXA/Node-RED 的身份与权限 | 页面、路由和 API 都受控，单点登录及反向代理可用。 |
| V005 | 现有 Node-RED 工程能复用多少 | 以当前源码、Flow、数据库和测试环境的只读审计为准，不用聊天历史代替证据。 |
