# Node-RED + FUXA 组态软件总体架构

> 状态：V0.1 架构基线（讨论结论，尚未经过本目录代码与运行环境验证）  
> 整理日期：2026-09-29  
> 来源：YC 项目《Node Red流程-设计计划(1)》专题的后期收口讨论。历史讨论中提到的 `E:\程序开发\智慧水务` 是现有业务工程；本文落在独立的 `E:\程序开发\组态软件` 项目，不能据此推定两处已经共享源码或数据库。

## 1. 目标与范围

建设一套面向实施工程师的工业组态与配置软件：通过工程对象配置，生成并部署 Node-RED 运行配置，利用 FUXA 完成工艺画面、2.5D 呈现、实时状态、人机控制、基础报警及按场景启用的趋势和简单报表。优先复用成熟软件，产品价值集中在统一工程模型、配置编译、稳定同步、验证、部署、回滚和诊断。

当前“数字孪生”目标是工艺、设备、状态、控制和报警的可视化映射；高精度三维、物理仿真和复杂模型属于后续扩展，不作为基础组态的验收前提。

## 2. 总体结构

```text
实施工程师
    │
    ▼
uniGUI 工程配置与集成界面
    │  工程树 / Tag / 属性 / 调度 / 权限 / 部署
    ▼
本产品的 SQLite 工程配置库（工程对象与可生成配置的事实源）
    │
    ├── Node-RED Adapter ──► 独立 Node-RED Runtime ──► PLC / 仪表
    │                              │ 采集、计算、上位协调、命令转发
    │                              ├──► 实时 Tag 通路 ──► FUXA Runtime
    │                              └──► 可选历史数据后端
    │
    └── FUXA Adapter ─────► FUXA 基础工程配置 / Tag 映射
                                       │
                                FUXA Editor 人工维护画面
                                       │
                                FUXA View / 报警 / 趋势 / 报表
```

这有两条需要分别验证的通路：**配置通路**把统一工程模型部署到 Node-RED 和 FUXA；**运行通路**让 Node-RED 的实时值、FUXA 的操作请求和 PLC 的真实反馈正确流动。两条通路目前都是设计目标，均未在本项目完成端到端验证。

### 组件职责

| 组件 | 职责 | 边界 |
|---|---|---|
| uniGUI | 工程配置、导航容器、部署入口、诊断入口、用户体验 | 不长期承担调度执行；不重做 FUXA 画布或 Node-RED 流程引擎 |
| 本产品 SQLite | Node、Tag、工艺关系、采集与控制参数、映射及可生成标准配置的事实源 | 与 FUXA 人工画面工程、FUXA 内部 SQLite、Node-RED 运行缓存分开 |
| 独立 Node-RED | PLC/仪表通讯、采集、计算、数据转发、上位调度、统一命令入口、运行 API | 不代替 PLC 联锁与安全保护；不要求实施人员日常手画大量 Flow |
| FUXA | Editor、View、Tag 展示、人机交互、基础报警及可选趋势/报表 | 不对同一 PLC 重复采集，不形成第二套主 Node-RED Runtime |
| PLC | 最终控制、联锁、保护、严格时序与硬实时逻辑 | 上位系统仅提出命令并观察反馈 |
| PostgreSQL 等 | 按场景承载长期 Tag 历史、专业报表、模型、3D 等扩展数据 | 不作为基础产品的工程配置库或必装依赖 |

## 3. 工程对象模型

- `Node` 表示区域、工艺、设备等工程对象，形成工程树。画面对象是 Node 在某一张图上的显示实例，两者不能混为一条记录。
- `Tag` 表示物理量、控制命令、计算量或常量；应有稳定 ID、名称、类型、单位、角色、读写属性、数据来源及质量/时效等必要元数据。具体字段与约束须在现状审计后设计。
- 设备与其配套 Tag 通常是 **1:N**；工艺与 Tag 可通过 `ProcessTag` 表达 **N:N 引用**。工艺的“本工艺 Tag”应显式配置；下属设备 Tag 可以作为查询视图汇总，不能自动充当工艺自身 Tag。关系不以 Node 内的 JSON/数组作为主存储。
- `TagDependency`、`NodeLink`、报警定义、调度定义、趋势/报表定义属于随需求细化的模型方向；当前不能把示意字段当作已实施表结构。
- FUXA 对接映射需要区分工程语义和产品字段，例如稳定 Tag ID、设备类型、图元槽位（Run/Fault/Current/Start）、报警映射、View/资源映射。FUXA 版本变化应主要由 Adapter 吸收。

## 4. 工程配置界面与同步

uniGUI 面向工程对象提供工程树、表格/UniGrid、属性编辑器（Property Inspector）和运行诊断。工程师配置一台泵及其 Tag、地址、周期、控制参数后，平台应校验并生成 Node-RED 配置，同时建立 FUXA 可用的稳定 Tag 目录和标准映射。

本节描述**统一工程配置的产品职责**，不是把工程配置限定为 Node-RED，也不是实施步骤清单。同一工程模型需要服务两个输出端：Node-RED 的运行配置和 FUXA 的基础对象/Tag 映射。下文的 Node-RED 与 FUXA 同步规则分别约束这两个输出端；各自的实施先后与验证门槛见第 8 节。

### Node-RED 部署边界

Node-RED 中**由本平台独占管理的 Flow/配置范围**可以从 SQLite 工程模型重新生成，并在校验后整体替换该范围再部署；这部分原则上不接受在 Node-RED Editor 中长期手工维护，因此通常不需要与人工内容做字段级合并。部署前仍须确认目标实例和管理范围，保留回滚版本，并防止覆盖不属于本平台的 Flow、凭据和运行设置。如果允许人员在受管范围内直接修改，则必须先检测偏离并明确由谁维护，不能一边允许手改、一边无提示覆盖。

这与 FUXA 不同：FUXA 工程同时承载平台同步的基础配置和工程师正式维护的画面内容，再同步必须比较并保护人工编辑。

**字段只设一个维护者。** 本产品 SQLite 维护设备、工艺、Tag、PLC 地址、采集周期以及可生成的标准配置；这些内容同步到 FUXA 后，FUXA 工程中也会有一份供其运行和编辑使用的配置副本。FUXA Editor 维护工程师手工制作的画面布局、位置、样式、管线及特殊交互；这些内容归 FUXA 工程所有，不因本产品 SQLite 是工程对象的事实源而被重新生成或覆盖。标准报警和基础绑定可由模型生成，项目特有的表现可在 Editor 完成。同步时必须保护人工编辑内容，支持增量、差异预览、备份和回滚；实现方式待 PoC 确认。

这里讨论的是**配置归谁维护**，不是断言 FUXA 的所有画面内容一定存放在某一张 SQLite 表中。FUXA 工程的实际持久化文件、数据库和 API 格式须在 PoC 中核验。

### FUXA 工程同步与手工修改

FUXA 工程是**可被两边修改的工作现场**：平台把设备、Tag 等基础数据直接配置进去，工程师随后会在 FUXA Editor 中编辑画面、绑定、报警及其他项目内容。不能每次部署时用平台生成的完整工程覆盖 FUXA 工程。

同步设计至少遵守以下规则，具体字段和接口仍待 PoC 确认：

1. **稳定身份**：平台对象 ID 与 FUXA 对象 ID 建立持久映射。更新使用原 ID，避免画面绑定因重新生成而失效。
2. **明确字段归属**：平台管理的字段才由平台更新；FUXA 人工管理的字段原样保留。对于可能由双方编辑的字段，先定义最终维护者和冲突策略，不能默认平台覆盖。
3. **部署前读取与比较**：读取当前 FUXA 工程，将“上次同步版本、当前 FUXA 版本、本次待部署配置”比较，识别人工改动、缺失对象和冲突；向工程师展示差异。
4. **冲突需显式处理**：若 FUXA 中的平台管理字段被人工修改，不静默覆盖，也不把改动悄悄回写为平台主数据；报告冲突，按已确定的字段归属处理。
5. **删除先检查引用**：删除或改名 Tag 前，检查画面、报警、趋势、报表和脚本等引用；有引用时阻止或安排迁移，避免悬空绑定。
6. **备份、验证与回滚**：同步前保留 FUXA 工程快照；同步后验证对象数量、ID 和关键绑定，失败时可恢复。是否能够原子更新由 FUXA 接口 PoC 判定。

上述规则表达产品要求，不表示 FUXA 现有 API 已提供完整的三方合并或事务能力。若接口只能写整个 Project，需验证是否能安全实现按对象合并；做不到时应缩小自动同步范围。

FUXA 自身的项目和报警持久化由 FUXA 管理。外部集成优先使用受支持的 API/项目接口，不直接写其内部数据库。FUXA Setup 中重复的连接、用户等配置在最终集成界面如何裁剪，需同时验证 UI、路由、API 与权限，不能靠隐藏菜单代替授权。

## 5. 运行通路与控制边界

运行路径原则：`PLC → Node-RED → FUXA Tag → View/报警`；控制路径原则：`FUXA/uniGUI → 稳定 Runtime 命令入口 → Node-RED → PLC → 反馈 Tag → FUXA`。具体传输可候选 WebAPI、MQTT、WebSocket 或 FUXA 对接节点，须以隔离环境验证双向值、质量、断线、重连、写入和反馈，不在此预定唯一实现。

FUXA 负责按钮、设定值、模式选择和操作反馈；Node-RED 负责命令路由、类型/范围/权限复核、超时及审计等上位职责；PLC 负责最终许可、联锁、保护、PID、顺控与严格时序。前端按钮置灰只是提示，后台与 PLC 仍需独立校验。浏览器 HMI 不承诺硬实时。

手动、定时与未来模型调度应汇入同一控制入口。调度规则由 uniGUI 配置并保存于工程模型，执行由 Node-RED 的通用调度模块承担，不能依赖 uniGUI 页面或进程中的长期 Timer。

## 6. 报警、趋势、报表与存储档位

基础档允许没有长期 Tag 历史库，支持实时监视、控制和按验证结果可用的基础报警。短期趋势、长期趋势、报表、报警历史是不同能力，应分别标明是否启用、数据来源、保留期和验收条件。不能因 FUXA 有内置 Historian 就默认把所有 Tag 再存一份。

若项目需要长期历史，现有候选路线是 Node-RED 写短期 SQLite 缓存并转存 PostgreSQL；PG 还可用于专业报表、模型与 3D 扩展。FUXA 的项目/报警存储与本产品 SQLite 配置库、可选 PG 历史库是不同职责。FUXA 历史趋势与报表能否直接、稳定地读取现有 PG 数据，是否需要只读 Provider/Adapter，以及报警历史能否独立于 Tag Historian 运行，都必须做 PoC；不把讨论中的可行性判断写成已交付功能。

当前不引入图数据库。工程树、工艺引用、依赖和上下游关系先用关系表表达；只有规模和查询需求给出证据后再评估专用图存储。

## 7. 集成与部署原则

- 面向人的 Node-RED Editor、FUXA Editor/View 可通过 URL/嵌入方式纳入 uniGUI 导航；单点登录、跨源、代理路由和直接访问控制要验证。
- 面向程序的配置、部署和查询走正式 API。Node-RED Admin API 用于配置和部署；运行控制通过本产品稳定的 Runtime API 契约，不把 Flow 内部节点暴露成外部接口。实时值应使用适合订阅/推送的通道，避免用高频 REST 轮询代替实时机制。
- 多平台部署优先采用原生数据库驱动，不以 ODBC 作为核心依赖。各组件版本与升级兼容以测试矩阵管理。
- 优先少量、可升级的 FUXA 适配与嵌入模式修改；FUXA 开源不意味着改造工作量和升级风险可以忽略。

## 8. 建设顺序与验证门槛

产品建设可先启动最小 uniGUI 主框架，但这不要求等界面完工才核对现有系统。Node-RED 现状只读核对（P0）和 FUXA 基础配置样例验证是**工程配置开发前的事实核实**，不是工程配置功能本身；两者应在 SQLite 模型定版前完成，以免后期改动对象 ID、Tag 语义和部署参数。之后建设统一工程配置界面与模型，先贯通 Node-RED 生成、隔离部署及运行核对，同时建立 FUXA 稳定 Tag 目录和映射；再完成 FUXA 工程增量同步、人工画面保护与运行联动。扩展功能按项目场景安排。下列验证事项嵌入相应阶段。

1. 对现有 Node-RED 配置、Runtime、数据与控制链路做**只读现状审计**，与历史讨论对账。
2. 在隔离环境完成 Node-RED ↔ FUXA 实时值、命令、反馈、断线/恢复 PoC。
3. 验证 FUXA Project/API 的增量写入、稳定 ID、人工画面保护、备份和回滚。
4. 验证 FUXA Alarm/ACK/History、趋势/报表在无历史库与 PG 扩展两种场景中的真实依赖。
5. 验证 uniGUI 嵌入、登录/权限、路由及多平台驱动。

任何“已支持”“已运行”的结论都应由当前源码、配置、环境与测试证据支撑，并记录到审计文档。
